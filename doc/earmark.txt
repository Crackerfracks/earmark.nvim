1. INTRODUCTION                                                *earmark-intro*

earmark highlights spans of text with labels and keeps those annotations
attached to the text while it changes: live edits, formatters, |:edit!|,
edits made outside Neovim, renamed files and undo.

Labels come from sets. The default sets are five generated palettes with
keys 1-99 ("vivid", "pastel", "earth", "metal", "cyber"); you can define
your own, in your config or in files (|earmark-sets|).

Changing an annotation's first or last words (`cw`, `ciw`, `s`, `C` ...)
keeps the new words in it, even when you change all of it. When annotated
text is rewritten the annotation is marked "stale"; when the text is deleted
it is "detached", never dropped, and comes back if the text returns. Annotations are plain JSON inside your project (`<root>/.earmark/`),
so they travel with the repository or notebook.

Requires Neovim 0.11 or newer.

==============================================================================
2. QUICKSTART                                             *earmark-quickstart*

1. Install it and call `require('earmark').setup()` (lazy.nvim: `opts = {}`).
2. Put the cursor on a word and type `3ghiw`. The word gets label 3.
3. Type `ghip` without a count: a prompt opens beside the paragraph. Type
   `12`, watch the colour on the text, press <CR>.
4. Press `<leader>mm` on an annotation and write a note. `q` saves it.
5. Rest the cursor on it: the hover shows its label, name and note. Press
   `<leader>mp` to list every annotation in the file.

Run |:checkhealth| earmark if something does not work.

4. THE LABEL PROMPT                                           *earmark-prompt*

`gh` without a count opens a one-line prompt beside the span. The span shows
the selected colour while you type and the list under the input narrows:

- digits match keys first, then the shades of that family (3 -> 3, 13, 23);
- anything else matches keys, then label names (fuzzy);
- empty input offers the last label, then labels already used in this file.

Each row shows the colour, the key, your name for the label and the colour's
name. With a count (3gh) there is no prompt; a hint under the cursor shows
which label the count picked while you type the motion (`prompt.count_hint`).

In the prompt:
  <CR>              apply the selected label
  <Tab>             like <CR>, then name the label; <Tab> or <CR> there
                    accepts the name
  <S-Tab>           back to the label stage
  <C-n> <C-p>       move through candidates (also <Down> <Up>; Normal j k)
  <C-s>             try the next label set
  <Esc>             Normal mode; <Esc> or q again cancels. While naming a
                    label you just chose: apply it without a name

A label with `choices` asks for a choice next, and a choice listed in
`text.when` asks for a line of text (|earmark-sets|). Labels whose `requires`
is not met are listed last, dimmed, with the reason.

Names are per file, and the project remembers them: a label named in one file
gets that name the first time it is used in another file of the project. The
name stage is pre-filled from what you called that label before: in this
file, elsewhere in the project, then anywhere. `prompt.ask_name` decides when
you are asked: "first_use" (default), "always" or "never".

Annotating exactly the same span again with another label asks first: `a` (or
<CR>) adds that label to it (both show and share one note), `s` makes a
separate annotation on the same text with its own note and tags, `r`
replaces its label (as `<leader>ml` does), <Esc> cancels. `.` repeats the
answer without asking. `prompt.confirm_stack = false` always adds, without
asking.

                                                       *earmark-color-names*
Colour names: every colour is named after the nearest of about 700 names from
the xkcd colour survey (public domain), by distance in OKLab. Labels of one
set get distinct names. They show in the prompt, the palette, the hover and,
for a label you haven't named, the statusline. `color_names = false` hides
them; `color_names = function(hex) return name end` supplies your own (nil
falls back); a set's label may carry `color_name = '...'`.

                                                       *earmark-color-adapt*
Light and dark colour schemes: the label colours are designed on a dark
background. On any other background each colour's lightness is shifted (hue
kept) so it stands out from the page as much as it does on dark; on a light
theme a highlight sits a little darker than the page. It follows
|:colorscheme| and 'background' changes. Labels themselves don't change, only
how they're drawn. `color_adapt = false` draws the exact colours.

5. NOTES, TAGS AND THE HOVER                                   *earmark-notes*

`<leader>mm` opens the note, a Markdown buffer in a float under the span (an
empty note starts in Insert mode). `q`, |:w|, <C-s>, leaving the float or
closing it saves; `<localleader>s` moves it to a split, `<localleader>f`
back. Clearing all the text removes the note. The note stays open while a
float opened from it has focus (an emoji or file picker), so the choice goes
into the note. When separate annotations cover the same text, `<leader>mm`
asks which note; a count (`2<leader>mm`) picks without asking.

Write `#tags` and `@identifiers` anywhere in a note and earmark picks them
up (not inside code or headings). `<leader>mt` adds tags without writing
them in the note, and lists every tag you have used.

The hover appears when the cursor rests on an annotation that has a name,
a note, tags, more than one label, or a stale or ambiguous status
(`hover.show_when = 'always'` for every annotation). It stays while you move
inside the annotation and goes away when you leave, type, scroll or start an
operator. Overlapping annotations are numbered innermost first. Moving the
cursor into the hover (a flash.nvim jump, a click, <C-w>w) onto a note line
opens that note for editing at the same spot; elsewhere in the hover, <CR>
opens the note of the annotation under the cursor.

End-of-line indicators show a pencil per note in the label's colour, and
with `<leader>mv` (or `indicators.tags = true`) the #tags and @identifiers
too; lines too long for them get them on a virtual line. Nothing goes in the
sign column.

6. FINDING AND REVIEWING                                        *earmark-find*

The pickers use snacks.nvim, then telescope.nvim, else |vim.ui.select()|
(`picker` forces one). Entries show the label name, text, tags and first
line of the note.                                         *earmark-query*
Query words for `:Earmark pick`, `:Earmark pick_all` and `:Earmark qf`:

  #tag  @ident  label:<key or name>  set:<name>
  status:<ok, stale, ambiguous or detached>  has:note  has:tags  has:zk
  anything else matches the text, the name or the note

The review list (`<leader>md`) offers, for each annotation that needs
attention: jump, compare, accept the current text, move it to a place its
text could be now (scored candidates), attach it to a selection, or erase.

7. WHAT THE HIGHLIGHTS MEAN                                    *earmark-looks*

- Overlapping annotations of different labels: the mix of their colours,
  underlined in the outer annotation's colour.
- Nested annotations of the same label: each inner level a deeper shade of
  the same colour.
- A second label: an undercurl in its colour. More labels cut the undercurl
  into equal runs, one per extra label (`overlap.extra = 'squares'`: small
  squares after the span instead).
- Stale: faded and underdashed. Ambiguous: underdotted.

`overlap = { style = 'top' }` turns mixing off: the smallest span is on top.

8. COMMANDS                                                 *earmark-commands*

                                                                    *:Earmark*
:Earmark [subcommand] [args]
    Without a subcommand, `info`. Every key action is also a subcommand.

    info               print the annotations under the cursor
    peek note tags toggle_hover toggle_indicators
    erase clear restore next prev next_same prev_same jump

    zk link            link the annotation to a note picked from `zk list`
    zk pick [query]    annotations in the project with a note; <CR> opens it
    zk sources         in a note: the annotations linked to it
    pick [query]       pick in this file (|earmark-query|)
    pick_all [query]   pick in the project
    qf [all] [query]   annotations into the quickfix list; `all`: project
    :'<,'>Earmark reanchor
                       attach the annotation being reviewed to the
                       selection
    scratch            reopen a scratch buffer you annotated earlier
    check              print how each annotation was placed; headless, exit
                       status 1 when any is detached:
                         nvim --headless file.md -c 'Earmark check' -c q
    color {#rrggbb|reset}
                       recolour the label under the cursor in this file
    set [name]         switch to a label set (no name: the next one)
    reload             re-read label sets and this file's annotations
    log                recent warnings and errors (also in
                       `<storage_dir>/earmark.log`)

9. CONFIGURATION                                              *earmark-config*

`require('earmark').setup(opts)` with any of these (defaults shown):
>lua
  sets = { 'vivid', 'pastel', 'earth', 'metal', 'cyber', 'feedback' },
  sets_dir = nil,          -- default ~/.config/earmark/sets; false to skip
  default_label = nil,     -- offered first, e.g. 'vivid/3' or 'review/q1'
  current = nil,           -- set a count resolves against (default: first)
  root_markers = { '.earmark', '.zk', '.git' },
  storage_dir = vim.fn.stdpath('data') .. '/earmark',
  stale_threshold = 0.6,   -- similarity below which an annotation is stale
  context = 32,            -- bytes of surrounding text kept on each side
  keys = { ... },          -- |earmark-keys|; false disables all
  prompt = { width = 44, max_rows = 8, ask_name = 'first_use',
             count_hint = true, confirm_stack = true },
  ui = { border = 'rounded' },
  note = { layout = 'float', width = 0.6, max_width = 100,
           height = { min = 5, max = 0.5 }, winblend = 0 },
  hover = { auto = true, delay = 120, show_when = 'named_or_note',
            max_width = 0.5, max_height = 0.5 },
  indicators = { mode = 'eol', tags = false, max_pencils = 3, identifiers = true,
                 show_empty = false },
  overlap = { style = 'blend',     -- or 'top'
              extra = 'split' },  -- or 'squares'
  export = { group_by = 'label', include_detached = true, format = nil,
             location = 'project' },  -- 'beside', a function, or a list
  zk = { cmd = 'zk', notebook = nil, dir = nil, template = nil,
         open = true },          -- |earmark-zk-notes|
  statusline = { digits = true, color_name = true },
  color_names = true,      -- false, or function(hex) -> name|nil
  color_adapt = true,      -- |earmark-color-adapt|
  picker = 'auto',         -- 'snacks' | 'telescope' | 'select'
  ignore_buftypes = { 'terminal', 'prompt', 'quickfix' },
  debounce_ms = 200,
<
`export.group_by` is 'label', 'position', 'tag' or 'time'; `export.format`
is a function `(list, ctx) -> lines` that writes the body yourself.
`export.location`: 'project' (<root>/.earmark/export/), 'beside' (next to
the file, as <name>.earmark.md), a function `(buf, ctx) -> path`, or a list
of these to write every one (you are asked about the first).

10. LABEL SETS AND SET FILES                                    *earmark-sets*

Strings in `sets` are generated numbered palettes, or `'feedback'`, the set
that ships with earmark (|earmark-feedback|). Named tables are your own:
>lua
  sets = {
    'vivid',
    critique = { labels = {
      { key = 'c', name = 'contradiction', color = '#e06c75' },
      { key = 'v', name = 'vague' },     -- colour picked for you
      'cut this',                         -- key = its position, 3
    } },
    mine = { generate = 'numbered',
             palette = { L = 0.7, C = 0.15, h0 = 200, zig = 0.04 } },
  }
<
A count resolves to the label whose key is that number, else the label at
that position.

Sets can live in files, one per file, named after the file:
`~/.config/earmark/sets/*.lua` or `*.json` (yours) and `<root>/.earmark/sets/`
(the project's; replaces a same-named set). Files are re-read when saved in
Neovim or when you come back after editing them elsewhere. Project Lua files
run only once trusted (|:trust|); JSON never runs code.

Labels for rubrics and forms:
>lua
  return { labels = {
    { key = 'q1', name = 'Accuracy', color = '#e06c75',
      choices = { { key = 'a', name = 'Correct' },
                  { key = 'b', name = 'Minor issue', color = '#e5c07b' },
                  'Major issue' },
      text = { when = { 'b', 'c' }, prompt = 'What is wrong?' } },
    { key = 'q1.1', name = 'Severity reason',
      requires = { q1 = { 'b', 'c' } } },
  } }
<
A label with `tags = { 'option-a' }` adds those tags to what it annotates. A
set with `tags = { 'todo', 'nit' }` has them listed first in `<leader>mt`.

                                                            *earmark-feedback*
The `feedback` set is for reviewing a plan, draft, demo or code. Keys 1-9, so
a count picks the label (`2ghip`):
  1 Keep  2 Change  3 Wrong  4 Question  5 Unclear  6 Cut  7 Idea  8 Prefer
  9 Later
Export with `<leader>me` to hand the feedback over as a Markdown list.

                                                            *earmark-set-for-file*
A set can belong to some files: put `<name>.earmark-set.json` in their folder
or a folder above it in the project.
>json
  { "extends": "feedback",
    "labels": [ { "key": "a", "name": "Option A", "tags": ["option-a"] } ],
    "tags": ["pick"], "expires": "2026-12-01" }
<
- `plan.earmark-set.json` applies to `plan.*`; `"files": ["drafts/*.md"]`
  picks others (globs relative to the set file's folder).
- Opening such a file switches to its set; leaving switches back.
  `"auto": false` only lists it first.
- It is listed only in its files. After `"expires"` it is not listed at all;
  annotations made with it keep their colours.
- `"extends"` starts from another set's labels; the same key replaces one.
- It never replaces a general set of the same name.

11. STORAGE                                                  *earmark-storage*

- A file inside a project: `<root>/.earmark/docs/<relative path>.json`,
  where <root> is the nearest directory with one of `root_markers`.
- Other files: `<storage_dir>/files/<absolute path>.json`.
- Scratch and unnamed buffers: `<storage_dir>/scratch/<id>.json`.

A record (schema version 2) holds the annotations, their notes and tags,
label names for that document, and a fingerprint of the text. The text itself
is a sibling snapshot under `snap/`, gitignored inside projects. Writes are
atomic; a record that cannot be parsed is never overwritten. Version 1
records are read and rewritten as version 2 on the next save. Records are not
merged: when two Neovim instances annotate one file, the last to save wins
(`:Earmark reload` reads what the other saved). When the root changes (a root
marker added or removed), a file's record moves on its next open.

Re-finding text, in order: the diff of the snapshot against the current
text; the exact text with the most similar surroundings; the closest fuzzy
match. When two places fit equally well the annotation is "ambiguous" and
the review list offers the candidates.

12. API                                                          *earmark-api*

Positions are 0-based `{ row, col }` byte columns, spans end-exclusive; buf 0
is the current buffer. A value is
`{ set = 'vivid', label = '3', choice = 'b'?, text = '...'? }`. Annotations
and tables you get back are copies: changing them changes nothing.

earmark.annotate({buf}, {s}, {e}, {value} [, {opts}])   *earmark.annotate()*
    Add an annotation; returns it, or nil when the span is empty. On exactly
    the span of an annotation, the label joins that one (second return value
    "added", or "same" if it has it); `{ separate = true }` makes a new one.
earmark.list({buf})                                         *earmark.list()*
    `{ { annotation = a, s = {row, col}, e = {row, col} }, ... }` in order;
    s and e are nil when detached. A Visual block lists one entry per row,
    each with `group` = the first row's id; that row holds the block's note
    and tags, and set_values and erase on any row act on the whole block.
earmark.at({buf}, {pos})                                      *earmark.at()*
    Annotations at {pos} (default: cursor), innermost first, in the same
    shape as |earmark.list()|.
earmark.get({buf}, {id})                                     *earmark.get()*
    The annotation, or nil when it isn't there.
earmark.set_note({buf}, {id}, {text})                   *earmark.set_note()*
    nil or '' clears the note.
earmark.set_tags({buf}, {id}, {tags})                   *earmark.set_tags()*
earmark.set_values({buf}, {id}, {values})             *earmark.set_values()*
earmark.erase({buf}, {ids})                                *earmark.erase()*
earmark.restore({buf})                                   *earmark.restore()*
    Restore the last erased batch.
earmark.rename_label({buf}, {value}, {name})        *earmark.rename_label()*
earmark.names({buf})                                       *earmark.names()*
    `{ ['vivid/3'] = 'Vague' }`
earmark.display_name({buf}, {value})                *earmark.display_name()*
    The name {value} goes by in {buf}: the document's name for its label,
    else the label's own name (a numbered label's is its key), then its
    choice: `'Accuracy · b Minor issue'`.
earmark.label({value})                                     *earmark.label()*
    `{ set, key, name, color, desc, tags }` of the value's label, or nil when
    there is no such label.
earmark.export({buf}, {opts})                             *earmark.export()*
    Markdown lines (opts as in `export`).
earmark.pick({opts})                                        *earmark.pick()*
    `{ scope = 'file'|'project', query = '#todo' }`
earmark.hover.show() earmark.hover.hide()                 *earmark.hover*
earmark.statusline({opts})                            *earmark.statusline()*
    `opts.hl`: the highlight group of the statusline section it goes in; its
    background is kept and it is restored after earmark's colours.
earmark.on({event}, {fn})                                     *earmark.on()*
    Run `fn(data)` on an event (|earmark-events|): 'Note' or 'EarmarkNote'.
    Returns the autocmd id.
earmark.zk.promote({buf}, {id}, {opts}, {cb})         *earmark.zk.promote()*
    Make a zk note for an annotation; `cb(err, path)` when done. An
    annotation whose note still exists keeps it (cb gets its path) unless
    `opts.force`. `opts.open` opens the note (default: `zk.open`).
earmark.zk.notebook({buf})                           *earmark.zk.notebook()*
    The notebook's path for a buffer or file path, or nil and the reason.
earmark.zk.path({annotation}, {buf})                     *earmark.zk.path()*
    Absolute path of the annotation's note, or nil when it has none.

Anything not listed here is internal and may change.

13. EVENTS                                                    *earmark-events*

|User| autocmds with `data = { buf, action, ids }`:
`EarmarkChanged` for every change, and one of `EarmarkAdd`, `EarmarkUpdate`,
`EarmarkErase`, `EarmarkRestore`, `EarmarkRepair`, `EarmarkNote`,
`EarmarkLoad`, `EarmarkZk` (an annotation was linked to a zk note, or
unlinked). `ids` is nil for `EarmarkLoad`, `EarmarkRepair` (an edit
detached, re-attached or changed the status of annotations) and a label's
name or colour changing. Setting what is already there fires nothing.
>lua
  require('earmark').on('Note', function(d) print(d.buf, vim.inspect(d.ids)) end)
<

14. ZK NOTES                                                *earmark-zk-notes*

earmark makes notes in a zk notebook (https://github.com/zk-org/zk) by
running the `zk` program; zk-nvim is not needed. Install zk (Arch:
`sudo pacman -S zk`) and create a notebook with `zk init`.

`<leader>mz` on an annotation makes a note with the annotated text as a
quote, the annotation's note, and a `[source](...#L12)` link back to the
line, and opens it in a split (`zk.open = false` to stay). The title is the
first line of the annotation's note, else the start of the quoted text. The
annotation keeps its note and remembers the zk note; the hover shows
`↗ zk <file name>`. After promoting, earmark offers to link the other
annotations in the file with the same text and label to the same note.

Pressed again, `<leader>mz` opens the note (or goes to the window showing
it) instead of making another. When the note's file is gone it asks whether
to make a new note or unlink it. In a note, with no annotation under the
cursor, it lists the annotations linked to that note. The subcommands:

  :Earmark zk           what `<leader>mz` does
  :Earmark zk new       a new note even if the annotation has one
  :Earmark zk link      link an existing note, picked from `zk list`
  :Earmark zk pick      the project's annotations that have a note; <CR>
                        opens the note (the query word `has:zk` filters
                        any picker the same way)
  :Earmark zk sources   the annotations linked to the note you are in

The note starts with frontmatter earmark writes, so zk indexes it:
>yaml
  ---
  title: "Why does the fox run?"
  tags: ["npc", "todo"]
  earmark:
    id: "..."
    set: "vivid"
    key: "3"
    label: "NPC"
    source: "notes/chapter-1.md"
    line: 12
  ---
<
The tags are the label's name, then the annotation's own tags and the
#tags in its note. `source` is the file's place in the notebook, or its
absolute path when it is outside. `line` is left out for a detached
annotation. The `[source]` link is relative to the note's folder (absolute
for a file outside the notebook), so zk's backlinks find the source too.
The annotation stores the note's path relative to the notebook.

The notebook is `zk.notebook` if set, else the nearest folder with `.zk`
above the file, else `$ZK_NOTEBOOK_DIR`. Options in `zk`:

  cmd        the zk program (default 'zk')
  notebook   the notebook folder
  dir        notebook subfolder for new notes, or a function that gets
             `{ buf, annotation, value, label, notebook, source }` and
             returns one, e.g. a folder per label
  template   your own zk template; it gets the body only and
             `--extra id=...,set=...,key=...,line=...`, and earmark writes
             no frontmatter
  open       open a new note in a split (default true)

The notebook as the project: `.zk` is one of `root_markers`, so annotations
on notes go in `<notebook>/.earmark/`, which zk ignores. A `.earmark` folder
nearer to the file wins (it comes first in `root_markers`), so don't create
one inside the notebook unless you want a separate project there.

|:checkhealth| earmark shows whether zk is installed, its version, and the
notebook for the current file.

==============================================================================
15. STATUSLINE                                            *earmark-statusline*

`require('earmark').statusline()` returns a statusline string, empty in
buffers earmark does not track: a swatch and the label the next `gh` uses,
the number of annotations and notes, a warning count for detached and
ambiguous ones, and for numbered sets the digits 1234567890 in their colours.
>lua
  -- lualine
  local em = require('earmark')
  sections = { lualine_x = { function() return em.statusline({ hl = 'lualine_x_normal' }) end } }
<

16. TROUBLESHOOTING AND FAQ                          *earmark-troubleshooting*

|:checkhealth| earmark checks the Neovim version, that the storage directory
is writable, the project root for the current directory, every record in it,
set files that failed to load, which optional plugins were found, and zk.

`:Earmark log` lists recent warnings and errors.

Nothing happens on `gh` ~
  `gh` is Select mode in stock Neovim; earmark takes it over. Check
  `:verbose nmap gh` for another plugin's mapping.

`ghh` waits before annotating ~
  `gh` is also an operator, so Neovim waits 'timeoutlen' to see whether `h`
  is the motion or the start of `ghh`. Press `ghh` quickly, or map `line`
  to something else.

The highlights vanished after a formatter ran ~
  They should be re-placed on the next change. Run `:Earmark check` to see
  where each one landed and `<leader>md` for the ones that need review.

A record won't save ~
  A record that can't be parsed is left untouched and saving for that
  buffer stops with a warning. Fix or move the file, then `:Earmark reload`.
